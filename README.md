# Объекты и задачи — мини-CRM для строительной компании

Постановщик заводит объекты (стройки) и задачи по ним, назначает исполнителя, принимает работу или возвращает на доработку. Исполнитель видит только свои задачи и объекты, где они есть, берёт задачу в работу и отправляет на проверку. Каждая смена статуса попадает в историю.

**Стек:** React 18, TypeScript, Vite, Tailwind, TanStack Query, React Hook Form + Zod, Supabase (PostgreSQL, Auth, RLS, SQL-функции).

Документы к сдаче:

- [EXPLANATION.md](EXPLANATION.md) — как устроена система и как защищены данные, простыми словами;
- [DECISIONS.md](DECISIONS.md) — решения и допущения там, где ТЗ допускает разные трактовки, и что не вошло.

## Запуск

Нужны Node.js 20.6+ и проект в Supabase (бесплатного тарифа хватает).

1. **База.** В Supabase → SQL Editor выполните `supabase/migrations/20261108120000_init.sql`.
   Или через CLI: `npx supabase init`, `npx supabase link --project-ref <ref>`, `npx supabase db push`.
2. **Отключите регистрацию:** Authentication → Sign In / Providers → выключить «Allow new users to sign up».
3. **Переменные окружения:**
   ```bash
   cp .env.example .env.local        # URL проекта и anon-ключ — для фронтенда
   cp .env.admin.example .env.admin  # URL и service_role — только для скрипта создания пользователей
   ```
   Значения — в Project Settings → API. Оба файла в `.gitignore`.
4. **Пользователи и демо-данные:**
   ```bash
   npm install
   npm run seed:users                # создаёт трёх пользователей с подтверждённым email
   ```
   Затем выполните `supabase/seed.sql` в SQL Editor: он назначит Ирине роль постановщика и создаст объекты и задачи.
   Без скрипта пользователей можно создать вручную: Authentication → Users → Add user (с теми же email и галочкой Auto Confirm).
5. **Приложение:**
   ```bash
   npm run dev                       # http://localhost:5173
   ```

### Проверки

```bash
npm test                  # правила доступных действий в интерфейсе (vitest)
npm run check:security    # 21 попытка обойти права прямыми запросами к Supabase
npm run build             # проверка типов и сборка
```

`check:security` входит под демо-пользователями с публичным anon-ключом — так же, как мог бы злоумышленник с этим ключом из браузера, — и пробует: читать и менять чужие задачи, менять статус в обход правил, принимать собственную задачу, вернуть на доработку без комментария, дописать, изменить или удалить историю, назначить себе роль, зарегистрироваться. Каждая попытка должна закончиться отказом базы; иначе скрипт напишет `FAIL`.

### Публикация

Сборка статическая (`dist/`), адреса вида `/#/sites`, поэтому работает на любом статическом хостинге без настроек сервера.
В репозитории есть workflow `.github/workflows/deploy.yml` для GitHub Pages: в Settings → Pages выберите Source «GitHub Actions», в Settings → Secrets and variables → Actions → Variables добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` и запустите workflow (или сделайте push в `main`). Для Vercel/Netlify: команда сборки `npm run build`, папка `dist`, те же две переменные.

## Как устроена защита

- **Права закрыты в базе.** На всех таблицах включён RLS: постановщик видит всё; исполнитель — только задачи, где он назначен, объекты с такими задачами и историю этих задач. Помимо политик, у роли `authenticated` отозваны лишние права: задачу через API можно создать и изменить только в полях «название», «описание», «объект», «исполнитель».
- **Статус меняется только функцией `change_task_status`.** Она проверяет, кто вызывает, текущий статус и обязательный комментарий, блокирует строку задачи от одновременных изменений, меняет статус и пишет историю. Колонку `status` напрямую обновить нельзя — нет права, а триггер дополнительно отклоняет смену статуса в обход функции даже от администратора.
- **История неподделываема.** Записи создают только функции базы, от имени `auth.uid()` и с `now()`; через API история доступна только на чтение, а изменение записей запрещено триггером для всех.
- **Роли.** Новый пользователь всегда исполнитель: роль из данных регистрации не берётся. Постановщика назначает администратор в базе. Открытая регистрация выключена.
- **Ключи.** Во фронтенде только публичный anon-ключ. `service_role` нужен лишь скрипту создания пользователей и хранится в `.env.admin`, который не попадает в репозиторий.
