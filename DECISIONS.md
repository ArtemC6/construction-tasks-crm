# Решения и допущения

## Что решил сам там, где ТЗ допускает варианты

**Роли и пользователи**
1. Роль хранится в таблице `profiles`. Профиль создаётся автоматически при добавлении пользователя; новый пользователь всегда исполнитель — роль из данных регистрации не берётся, чтобы её нельзя было подставить. Постановщика назначает администратор в базе (`update profiles set role = 'manager' ...`). Экрана управления пользователями нет — в ТЗ его нет, а пользователей создают вручную.
2. Исполнитель видит в базе только свой профиль и профили постановщиков (имена в задачах и истории). Список коллег-исполнителей ему не нужен.
3. Принять или вернуть задачу может любой постановщик, а не только её автор: постановщиков может быть несколько, и они могут подменять друг друга.

**Задачи**
4. Исполнитель обязателен при создании задачи: без исполнителя задача не может двигаться по статусам. Назначить можно только пользователя с ролью «Исполнитель» — проверяет база.
5. Постановщик может редактировать задачу (название, описание, объект, исполнитель) в любом статусе, в том числе переназначить. После переназначения прежний исполнитель теряет доступ к задаче. Переназначение не пишется в историю: по ТЗ история — это смены статусов.
6. Автор и дата создания задачи ставятся базой и не меняются; статус при создании всегда «Новая», даже если прислать другой.
7. Комментарий можно оставить при любой смене статуса; при возврате на доработку он обязателен (пустой или из пробелов не принимается).
8. Постановщик не может сам перевести задачу «в работу» или «на проверку» за исполнителя — эти переходы по ТЗ делает только назначенный исполнитель.
9. Одновременные клики (два постановщика разом нажали «Принять» и «Вернуть») не создают двойных переходов: функция смены статуса блокирует строку задачи на время проверки.

**Объекты**
10. В карточке объекта исполнитель видит только свои задачи на этом объекте, а не все: иначе он увидел бы чужие задачи.
11. Удаление объекта удаляет его задачи, удаление задачи — её историю (удалять объекты и задачи постановщику разрешено ТЗ, а история без задачи бессмысленна). Удалить или изменить отдельную запись истории нельзя никому. Перед удалением интерфейс переспрашивает.

**Техническое**
12. Смена статуса — отдельная функция базы `change_task_status`, а не обычное обновление строки: так проверка перехода и запись истории происходят в одной транзакции и не могут разойтись. Прямое изменение колонки `status` запрещено правами, а триггер дополнительно отклоняет его даже для администратора.
13. Правила переходов продублированы во фронтенде (`src/lib/status.ts`) только для показа нужных кнопок. Источник правды — база; интерфейс показывает её сообщение об ошибке, если что-то не так.
14. Маршрутизация через `#` (`/#/sites`): приложение работает на любом статическом хостинге без настройки сервера.
15. UI — Tailwind без компонентной библиотеки: для пяти экранов хватает нескольких своих компонентов, а дизайн по ТЗ не оценивается.

## Что не вошло

- Обновление в реальном времени (Realtime): изменения другого пользователя видны после перехода между экранами или обновления страницы.
- Экран управления пользователями и ролями, сброс пароля.
- Постраничная загрузка и поиск — при объёмах одной компании пока не нужны.
- Журнал изменений полей задачи (кроме статусов) и «мягкое» удаление с возможностью восстановления.
- Сквозные браузерные тесты: логика прав проверяется скриптом `npm run check:security` прямо на базе, правила кнопок — unit-тестами.
